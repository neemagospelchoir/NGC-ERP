# PHASE_8_3.md — Phase 8.3 Deliverable
## Neema Gospel Choir (NGC) ERP — Operations: Gate Pass

Continuation of the Development Control Rule sequence and of Phase 8's decomposition (docs/PHASE_8_1.md's introduction). **8.3 Gate Pass** (this document) follows 8.1 (Vendors + Inventory/Assets) and 8.2 (Uniform Management). Remaining: 8.4 Technical Rider & Playlist, 8.5 Logistics.

## 1. Scope

In scope:
- Gate pass registry (`gate_passes`/`gate_pass_items`, PRD §7.6): create a gate pass for an event (responsible person, department, expected departure/return), add equipment line items (which performs the actual equipment-to-event assignment — see §2.1), submit it into its configured 2-step approval chain, decide each step, check out, mark in transit, and record per-item returns (good/damaged/lost), matching the PRD's full status lifecycle (`pending_approval → approved/rejected`, then `checked_out → in_transit → returned/partially_returned/damaged/lost`).
- **Reuse of the generic workflow engine for a second real caller** (the first was Invitations, Phase 7.5) — the seeded "Standard Gate Pass Approval" chain (technical_manager → secretary, matching PRD §7.6 and §6's Permission Matrix exactly) already existed in `supabase/seed/001_reference_data.sql` since Phase 4, unused until now.
- **A real, necessary schema change**: `start_gate_pass_workflow`, a new SECURITY DEFINER RPC (migration 0029) — see §2.2 for why the existing generic `startWorkflow()` path doesn't work for this module.
- **A real, pre-existing bug fix** to Phase 7.5's `record_workflow_decision` (migration 0030) — see §2.3. This was not introduced by this phase; it was discovered while validating this phase's own new SQL against a real Postgres instance for the first time.

Explicitly deferred, named here rather than silently skipped:
- **A member/event/asset picker with name search** — `createGatePass`'s `eventId`/`personResponsibleId` and `addGatePassItem`'s `assetId` are plain text fields (paste the ID from that record's own page), the same deliberate simplification as Assets'/Uniforms' equivalent fields (docs/PHASE_8_1.md §1, docs/PHASE_8_2.md).
- **QR-code scan-and-resolve flow** — `gate_passes.qr_token` is generated and displayed read-only; no scanning/checkpoint-lookup endpoint is built this phase (ARCHITECTURE.md's QR section names this as its own later capability, not something any module has built yet).
- **PDF gate pass export** — PRD §7.6 implies a printable gate pass document; PDF generation is a named, separate later capability (ARCHITECTURE.md, PRD §7 line on "PDF generation") not built for any module yet.
- **Repair tracking / partial-quantity returns** — matches Assets' and Uniforms' own deferrals (docs/PHASE_8_1.md §1, docs/PHASE_8_2.md §1); a `damaged` gate pass item stays out of circulation until manually corrected.
- **Removing/editing an already-added item** — items can only be added, matching the append-only pattern of Asset/Uniform assignments; correcting a mistaken item requires an administrator's direct intervention.
- **Gate Pass 8.5's Logistics/Trips and 8.4's Technical Rider & Playlist** — unrelated tables, named in docs/PHASE_8_1.md's introduction.

## 2. Architecture

### 2.1 Adding a gate pass item IS the "equipment assigned to an event" action — by reusing Assets' own function, not re-implementing it

PRD §7.6 opens with "Technical Department assigns equipment to an approved event ... auto-generates a Gate Pass." Rather than building a separate assignment path for gate passes, `packages/services/src/gate-passes/add-item.ts`'s `addGatePassItem` calls the existing, already-tested `inventory.assignAsset` (Phase 8.1) with `targetType: 'event'` — reusing its availability check, its unconditional `disposed`-is-terminal rule, and the hard database-level double-booking backstop (`uq_asset_assignments_no_concurrent_event_booking`, 0010) rather than re-implementing any of it. If `assignAsset` throws, the gate pass item is never created, so the two records can never disagree about whether the equipment was actually assigned. Symmetrically, `lifecycle.ts`'s `returnGatePassItems` looks up the matching OPEN `asset_assignments` row (via `listAssignmentsForTarget`) and calls `inventory.returnAssignment` on it when an item is returned, keeping both systems in sync without a second, independent condition-tracking mechanism.

A security review of this phase found a latent (not currently reachable) inconsistency this reuse introduces: `addGatePassItem` is conceptually gated on `inventory.gate_passes.manage` (via `gate_pass_items_write_scoped` RLS), but the `assignAsset` call it makes is gated by a *different* permission pair (`inventory.assets.manage` OR `technical.equipment.assign`). Today every role holding `technical.equipment.assign` (only `technical_manager`) also holds `inventory.gate_passes.manage`, so this cannot currently be exploited — but it is flagged, with a full explanation, in `add-item.ts`'s own doc comment rather than silently left implicit, and is not "fixed" with a bolted-on app-layer permission check, since this codebase's established convention (`auth/authorize.ts`'s own doc comment) reserves that kind of check for service-role-client operations, not normal RLS-scoped writes — adding one here would duplicate RLS without changing the real boundary.

### 2.2 A new SECURITY DEFINER RPC was necessary to start the workflow — a distinct gap from the one Phase 7.5 already fixed

The seeded "Standard Gate Pass Approval" chain is `technical_manager → secretary`, matching PRD §7.6 ("requiring Technical Manager then Secretary approval") and §6's Permission Matrix ("Technical Manager: Create, Approve (tier 1)") exactly. But `workflow_instances_write_service` RLS (0019) requires `management.approvals.manage` to INSERT a `workflow_instances` row — and per the seed, `technical_manager` (who both creates a gate pass and is its own tier-1 approver) holds only `management.approvals.read_all`, never `.manage` (only secretary/chairman/vice_chairman/super_admin hold `.manage`). This is a different shape from Invitations' equivalent call (`startInvitationApproval`, a plain RLS-scoped insert): there, Secretary happens to hold BOTH the permission that starts the review and `management.approvals.manage`, so the generic path already works. For Gate Pass, nobody who would naturally create one holds `management.approvals.manage` — the generic path is unusable by design, once you look at who the PRD actually names as the creator, not by oversight.

Migration 0029 adds `start_gate_pass_workflow`, a SECURITY DEFINER RPC — the same "narrow, purpose-built escape hatch" pattern as `record_workflow_decision` (0028) and `apply_disciplinary_membership_status` (0026). It re-verifies, itself, that the caller holds `inventory.gate_passes.manage` (never a client-supplied flag), that the gate pass exists, is still `pending_approval`, has at least one line item, and has no existing workflow instance, before creating the instance against the seeded definition. `packages/services/src/gate-passes/workflow.ts`'s `submitGatePassForApproval` is the only caller. Deciding each step afterwards still goes through the existing, unmodified `record_workflow_decision` (0028/0030) — its authorization logic needed no change; only a column-qualification bug in its SQL text did (§2.3).

### 2.3 A real, pre-existing bug in Phase 7.5's `record_workflow_decision` — found by testing against real Postgres for the first time

This phase is the first to validate its own new SQL against a real, locally-running Postgres instance (`scripts/db-migrate.sh` + manual RPC calls via `psql`) before shipping, rather than relying solely on the Playwright e2e mock server (a hand-written JS re-implementation of the state machine) and the `@ngc/services` unit-test fake client — neither of which model plpgsql's variable/column name resolution rules. Doing this immediately surfaced a genuine, already-shipped defect: `record_workflow_decision`'s (0028) `RETURNS TABLE` clause declares OUT parameters named `id`, `status`, `current_step_order`, `record_type`, and `record_id`. plpgsql's default `variable_conflict = error` behavior treats any bare reference to a column with the same name, anywhere in the function body, as ambiguous against that OUT parameter — every `where id = p_workflow_instance_id` in the function (the initial `select ... for update`, and all three `update ... where` statements) was left unqualified. **Every real invocation of this function has therefore failed immediately** with `column reference "id" is ambiguous`, since it shipped in Phase 7.5 — confirmed directly: `select * from record_workflow_decision(<uuid>, 'approve', null)` against a live instance fails on line 1 of its body, before it can do anything.

This means Invitations' entire approval-chain decision flow (Phase 7.5) has never actually worked against a real database, despite passing every unit test and e2e test — because neither of those test surfaces executes this function's real SQL text. Gate Pass's own new `start_gate_pass_workflow` (0029) would have shipped with the identical class of defect had it not been checked the same way before it was ever run for real — it was written correctly the first time (every column reference is table-qualified), but this was verified, not assumed.

Migration 0030 re-issues `record_workflow_decision` via `create or replace function` with every WHERE-clause `id` reference qualified as `workflow_instances.id` — diffed directly against 0028's original text to confirm this is the ONLY change: authorization logic (role/user match, decision handling, `errcode`s) is byte-for-byte identical. No new migration for Invitations was needed beyond this — it is the same function, same signature, same grants, just corrected.

This also surfaced a second, smaller gap: `packages/db/scripts/generate-types.mjs`'s RPC type list is hand-maintained, not introspected from `pg_proc`, and had already fallen out of sync — three prior RPCs (`find_member_by_number_for_discipline`, `apply_disciplinary_membership_status`, `record_workflow_decision`) were hand-added directly to the checked-in `database.types.ts` but never added to the generator script itself, so re-running `pnpm gen:types` (done for this phase, to pick up `start_gate_pass_workflow`'s signature) silently deleted their type signatures. Fixed by adding all three to the script alongside the new one, with a comment explaining the maintenance obligation going forward.

### 2.4 The two-step approval chain's decision UI reuses Invitations' established pattern exactly

`[id]/page.tsx`'s "Your decision" section is gated on `workflow.isCurrentStepFor(instance, {id, roleCodes})` — the shared helper Phase 7.5's own security review centralized after finding two call sites checking only the role-code half of a step (see `workflow/match-step.ts`'s own doc comment) — shown regardless of `canManage`, since the Secretary (step 2) holds only `inventory.gate_passes.read`, not `.manage`. This is the identical shape as Invitations' `isCurrentApprover` block, reused rather than re-derived.

## 3. UI

- `/gate-passes` — gated on `inventory.gate_passes.manage`/`.read` (Technical Manager, Inventory Officer, Secretary per the seed), a UI convenience narrower than `gate_passes_select_internal`'s `auth.uid() is not null` RLS baseline, consistent with Vendors/Assets' precedent (docs/PHASE_8_1.md §4) — not the access boundary itself.
- `/gate-passes/[id]` — read access is not application-gated beyond the page-level permission check (same "trust Postgres" pattern as the cross-module Approval Center and Uniforms' assignment history, docs/PHASE_7_5.md, docs/PHASE_8_2.md). Add-item/submit/checkout/in-transit/return forms are gated on `canManage`; the decision form is gated on `isCurrentStepFor` regardless of `canManage` (§2.4).
- `layout.tsx` — added to the existing "Operations" nav group (Vendors, Assets, Uniforms, now Gate Passes), gated like Vendors/Assets (no ordinary member has a self-service reason to browse the gate pass registry, unlike Uniforms).

## 4. Security review

An adversarial review (Agent-dispatched, independent of the implementation), covering: whether `start_gate_pass_workflow` (0029) has the same column-ambiguity defect just found and fixed in 0028 (it does not — verified table-qualified throughout); whether 0030's diff against 0028 changes anything beyond column qualification (it does not — diffed directly, authorization logic is unchanged); whether a plain member can bypass the UI to create/submit/decide/checkout/return a gate pass (no — every write path is RLS-gated, traced through `gate_passes_write_scoped`, `gate_pass_items_write_scoped`, and the re-verifying 0029/0028 RPCs); whether any client-supplied value is trusted for authorization (no — `assignedBy`/`actingUserId`/`actingUserRoleCodes` are all server-derived); and whether `returnGatePassItems`' cross-reference into `asset_assignments` could touch a different gate pass's assignment (structurally impossible, given the DB's own partial unique index) — found no Critical/High issues, and two Low/Low-Medium items, both accepted as documented limitations rather than "fixed" with an inconsistent workaround:

- **The permission-set mismatch between `gate_pass_items_write_scoped` and `asset_assignments_write_inventory`** (§2.1) — not reachable under the current seed, flagged in `add-item.ts`'s own doc comment for if a future custom role ever splits `technical.equipment.assign` from `inventory.gate_passes.manage`.
- **A TOCTOU race in `addGatePassItem`'s "no changes after submission" check** — a plain, unlocked read; a concurrent add-item and submit-for-approval could interleave. Both require the same permission, so this is a data-integrity nuisance, not a privilege boundary, matching this codebase's established practice of fixing races only where the harm crosses a security boundary (docs/PHASE_8_1.md §2.3, docs/PHASE_8_2.md §2.3).

Reviewed and explicitly not changed (documented, not overlooked):
- The `auth.uid() is not null` SELECT RLS baseline on `gate_passes`/`gate_pass_items` (0011) — an inherited Phase 4 pattern, same class as the already-accepted limitations on Invitations/Assets/Vendors/Uniforms.
- No automated database-integration test suite exists in this codebase to catch real-Postgres-only bugs like §2.3's class automatically — this phase's manual `psql`-based verification (seeding test users/roles, calling both RPCs directly, walking the full 2-step chain to `approved`) is not itself repeatable by CI. Flagged as a genuine open gap (§7), not silently left uncaught next time.

- No member/event/asset picker with name search — plain-text ID entry today (§1).
- No QR scan-and-resolve flow, no PDF gate pass export (§1) — both are named, separate, later capabilities per ARCHITECTURE.md, not unique to this module.

- The permission-set mismatch flagged in §2.1/§4 — not reachable today, but worth resolving explicitly (either by adding `inventory.gate_passes.manage` to any future role also granted `technical.equipment.assign`, or by unifying the two RLS policies) before that combination is ever actually granted.

- **No automated database-integration test suite** to catch real-Postgres-only bugs like the one found and fixed in §2.3 — this phase's manual `psql` verification is not repeatable by CI today. A future phase should consider a lightweight `pg_prove`/`pgTAP`-style suite, or at minimum a CI step that spins up Postgres, applies migrations, and smoke-calls every SECURITY DEFINER RPC once.
