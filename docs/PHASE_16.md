# PHASE_16.md — Phase 16 Deliverable

## Neema Gospel Choir (NGC) ERP — Dependency Security Remediation

Phase 15 (Deployment) was the last phase `ARCHITECTURE.md` §19's roadmap names. After Phase 15 and the standalone 14.4 capstone review were both complete, the user's own instruction ("Proceed next phase") had no further roadmap position to point to, so — consistent with this project's established convention for scope not defined by the PRD/architecture (Phase 14's own decomposition, decided the same way) — a clarifying question was asked. The user answered with an explicit deferral to judgment. Given that deferral, a `pnpm audit` across the whole workspace was run as the concrete, checkable starting point, rather than inventing a speculative feature. It surfaced roughly thirty real advisories, the great majority of them ~20 Next.js CVEs (several high severity: request smuggling, cache poisoning, SSRF, DoS, XSS) affecting the installed `next@14.2.35`, patched only by upgrading to `next@>=15.5.21`. This phase is that remediation.

## 1. Scope

In scope:

1. **Upgrade `next`/`eslint-config-next` 14.2.35 → 15.5.23** in `apps/web` — the single highest-value fix, closing ~20 of the ~30 findings in one change. 15.5.23 is the newest release on the `backport` dist-tag, i.e. the actively-maintained 15.x security-backport line, deliberately chosen over jumping to the `latest` tag (Next 16, a new major with its own breaking-change surface) — this phase fixes a known vulnerability set, not everything a version bump could theoretically touch.
2. **Fix every breaking change the major-version bump introduced** in `apps/web`'s own code: Next 15's async Dynamic APIs (`cookies()` and every page/layout's `params`/`searchParams`), and a genuine runtime regression under the new bundler in the one place `apps/web` does something unusual with React (`@react-pdf/renderer`'s custom reconciler) — detailed in §2.
3. **Fix the remaining findings that are actually fixable without a major bump elsewhere**: a moderate `uuid` buffer-bounds-check CVE (via `pnpm.overrides`, workspace-wide), and — found only after re-auditing post-upgrade, since these are Next's *own* internally-pinned dependencies rather than anything this project chose — high-severity `postcss` and `sharp` CVEs vendored inside `next@15.5.23` itself (also via `pnpm.overrides`).
4. **Document and deliberately defer the one finding with no fix available at all**: an `image-size` denial-of-service pair (used only by Metro, `apps/mobile`'s bundler, at build time) with no patched release yet published upstream — see §7.

Explicitly not attempted this phase: upgrading to Next 16 (a new major, out of scope for a security-remediation phase — see point 1 above), and touching `react`/`react-dom` versions (Next 15.5.x's own peer-dependency range accepts the already-installed React 18, so no forced React 19 migration was needed or performed).

## 2. Architecture

### 2.1 Async Dynamic APIs

Next 15's headline breaking change: every Dynamic API that depends on request data — `cookies()`, `headers()`, `draftMode()` (`next/headers`), and `params`/`searchParams` in page/layout/route props — became `Promise`-returning. `apps/web` has exactly one call site for `cookies()` (`lib/supabase/server.ts`'s `createClient()`, the single binding point every Server Component and Route Handler goes through for auth — see that file's own doc comment), converted to a proper `async function` with `await cookies()`. The official `@next/codemod` tool's own fallback for this exact call site is a type-cast escape hatch (`UnsafeUnwrappedCookies`) that Next's own documentation marks temporary and slated for removal — deliberately not used here in favor of the correct `async`/`await` conversion. Converting `createClient()` to `async` cascaded to its ~159 call sites across 88 files (`const supabase = createClient()` → `await createClient()`), applied via a global, mechanically-verified find-and-replace (0 remaining un-awaited call sites afterward). The 36 files destructuring `params`/`searchParams` were converted by the official `@next/codemod next-async-request-api` transform, which correctly rewrites this specific, well-defined pattern.

### 2.2 The PDF-export regression — root cause and fix

`reports/export/route.ts`'s `pdf` branch (`render-pdf.tsx`, `@react-pdf/renderer`) started failing every request under Next 15 with a runtime "Minified React error #31: Objects are not valid as a React child" — while the same route's `csv`/`xlsx` branches, and every other page in the app, kept working. This looked at first like a classic "duplicate React copy" bug, but the usual causes didn't hold up: `pnpm why react` shows one single `react@18.3.1` throughout the dependency graph; an isolated script using the exact same `@react-pdf/renderer` + `react@18.3.1` combination outside of Next entirely rendered correctly; and `serverExternalPackages` (Next's documented fix for "a package with its own React reconciler breaks under App Router bundling") made no difference at all, with or without it.

Direct instrumentation of both `@react-pdf/reconciler` (which dynamically dispatches to one of three internal reconciler builds based on a parsed `React.version` string) and the actual element object `render-pdf.tsx` was about to render found the real cause: `React.version` reads `18.3.1` correctly everywhere, and it is genuinely the same `react` module instance in both places — but the *element itself*, as built by this file's JSX (compiled through Next's own App Router server-components toolchain), carries `$$typeof: Symbol.for('react.transitional.element')`, not the `Symbol.for('react.element')` tag the plain node_modules `react@18.3.1` package — and therefore `@react-pdf/reconciler`'s own element-validity check — expects. Next's App Router compiles every file under `app/` against its own internally-vendored React build (needed for React Server Components support), which is not the same build as the `react@18.3.1` sitting in node_modules even though both report the same version string. That vendored build already uses the newer element-tag scheme; a plain npm `react@18.3.1` does not. Any element this file creates — via JSX or via a normally-imported `React.createElement` — is therefore invisible to a reconciler that checks for the older tag, regardless of bundler settings.

The fix, applied only to this one file: build the `@react-pdf/renderer` component tree using `React.createElement` from a `require('react')` call written as `eval("require")("react")` — a dynamic call bundlers cannot statically see or rewrite, so it reaches Node's real module resolution instead of Next's App Router aliasing, landing on the genuine node_modules `react@18.3.1` and its correct legacy element tag. This is the standard "force a truly native, unaliased require" technique used elsewhere in the ecosystem to defeat exactly this class of bundler substitution (native-binding loaders, some ORMs); it is not a one-off hack invented for this bug. Confirmed empirically at each step (a `console.error` of `$$typeof` before and after the change) before being made permanent; all diagnostic instrumentation — in this file and in a temporary patch to `@react-pdf/reconciler` itself, used only to prove the hypothesis — was reverted before landing. `serverExternalPackages` was removed again from `next.config.js` once proven not to be the fix, keeping the diff to what's actually needed.

### 2.3 Dependency overrides (`pnpm.overrides`, root `package.json`)

- `uuid: "^11.1.1"` — a moderate buffer-bounds-check CVE affecting `uuid`'s `v1()`/`v6()` code paths, reached transitively via `exceljs` (apps/web's Excel-export dependency, production) and via Expo's `xcode` build tooling (apps/mobile, dev-only). The only `uuid` API this project actually calls is `v4()`, unaffected by and stable across the major-version bump; confirmed via `pnpm why uuid` that both paths now resolve to the patched version.
- `postcss: "^8.5.23"` — four CVEs (one moderate XSS, two high path-traversal/arbitrary-file-read, one moderate incomplete-fix) in `postcss@8.4.31`, a version Next.js pins as a *hard, non-range* dependency of its own — not a choice this project made, and not fixable by staying within the 15.5.x line, since 15.5.23 is already the newest release on that line and still pins the same old `postcss`. `8.5.23` is the version Next's own next major release (16.3.0) itself later moved to, which is the strongest available evidence the override is safe: the framework's own maintainers use that exact version internally with no special handling.
- `sharp: "^0.35.0"` — four high-severity libvips CVEs in `sharp@0.34.5`, an *optional* dependency of `next` used only by `next/image`'s self-hosted image-optimization path. `apps/web` does not use `next/image` anywhere (`grep` confirms zero call sites), so this had no live exploitable path in this app today — fixed anyway, at zero behavioral risk, since nothing in this codebase calls `sharp`'s API directly and the override only changes what Next's own optional internal usage would resolve to if that path is ever exercised in the future.

No UI changes. This phase is a dependency/runtime remediation; every page, form, and permission gate behaves identically to Phase 15's end state. The only user-visible difference is that PDF report exports, which were broken by the upgrade mid-phase, work again by the end of it.

## 4. Security review

This phase *is* a security review in its own right (a dependency-vulnerability remediation), so its own review is the re-audit in §6 confirming the finding count actually dropped, plus the explicit reasoning in §2.3 for why each override is safe (uuid: unused API surface; postcss: same version the framework's own next major adopted; sharp: zero live call sites in this app). No new attack surface was added — no new route, no new RLS-relevant table or policy, no new SECURITY DEFINER function. The one thing worth naming as a self-review finding: the `eval("require")` pattern in `render-pdf.tsx` (§2.2) is unusual enough to warrant flagging for a future reader rather than leaving it looking like stray debug code — it is now the file's most heavily-commented section, explaining exactly why it exists and what breaks without it.

- `pnpm typecheck` — all 8 workspace packages pass, including after the Next 15 upgrade's cascading `async` conversions and a `@types/react` packageExtensions update needed to keep a single unified React types version.
- `pnpm lint` — all 8 workspace packages pass, including `apps/web`'s `next lint` (0 warnings/errors; its own "next lint is deprecated in Next.js 16" notice is informational, noted in §7, not an error).
- `pnpm --filter @ngc/services test` / `pnpm --filter @ngc/mobile test` — 458/458 and existing mobile unit tests, unaffected.
- `pnpm --filter @ngc/web build` — a real `next build` (production bundle), clean, all 68 routes.
- `apps/web`'s full Playwright e2e suite — **84/84 passing**, including `reports.spec.ts`'s export test (the one spec that caught the PDF regression in the first place, then confirmed the fix), re-run once more after the `postcss`/`sharp` overrides landed to rule out any second-order regression from those.
- `pnpm audit` after: **2 advisories remaining**, both `image-size` (DoS, no patched version exists — see §7). Every other finding present at the start of this phase, plus two more this phase's own upgrade incidentally introduced (`postcss`, `sharp`, vendored inside `next` itself), are fixed.

## 7. Open issues / deferred, not overlooked

- **`image-size`: ICNS/JXL/HEIF-parser denial-of-service (2 advisories, high).** Reached via `metro@0.84.4`, Expo/React Native's JavaScript bundler (`apps/mobile`'s build tool, not shipped in any built app or web bundle — see `pnpm why image-size`, which resolves this dependency exclusively through Metro). At the time of this audit, the advisory's own `patched_versions` field reads `<0.0.0` — i.e. **no fixed release exists yet**, even at the latest available `image-size@2.0.2`, so this cannot be remediated via a version bump today. Exploiting it would additionally require getting a malicious image file into a local `expo export`/dev-server bundling step, not something reachable by an external attacker against a deployed instance. Left as a known, tracked gap rather than silently ignored; revisit by re-running `pnpm audit` after Metro's own next release, since the fix (when one ships) will arrive as a `metro` version bump, not a direct `image-size` override (Metro doesn't declare it as a range this project can safely override around without risking API mismatch against Metro's own pinned usage).
- **`next lint` deprecation notice** ("next lint is deprecated and will be removed in Next.js 16"). Informational only — `apps/web` still lints clean. Worth a follow-up migration to the plain ESLint CLI (`npx @next/codemod@canary next-lint-to-eslint-cli .`, Next's own documented path) before any future Next 16 upgrade, but not itself a security finding and not this phase's job to force.
- **Next 16.** The `latest` npm dist-tag has already moved to a new major (16.3.0 at the time of this phase). Not evaluated for adoption here — this phase's mandate was closing known CVEs on the already-installed major, not chasing the newest release; a future phase can evaluate Next 16 on its own breaking-change/benefit merits.
