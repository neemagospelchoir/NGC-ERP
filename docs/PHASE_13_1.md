# PHASE_13_1.md — Phase 13.1 Deliverable
## Neema Gospel Choir (NGC) ERP — Reporting: Engine + Member/Attendance/Invitation Reports

Phase 13 ("Reporting") begins with this sub-phase. PRD §11 names fourteen report subjects (member, attendance, contribution, expense, vendor, inventory/asset, event, invitation, logistics, technical, uniform, discipline, HR, management) each needing Monthly/Quarterly/Yearly/Custom filtering and PDF/Excel/CSV export; PRD §15's MVP/V2 tiering names only "core Reporting (member, attendance, invitation)" as MVP, with the full fourteen-module engine and separately "Management KPI dashboards" as two distinct V2 features. 13.1 builds the reporting engine itself — the piece every other report will reuse — plus exactly those three MVP reports; 13.2 (this same phase, no fresh authorization needed) extends coverage to the rest of PRD §11's list.

## 1. Scope

In scope:
- **A generic, parameterized report engine** (`packages/services/src/reports/`), not fourteen bespoke exports: a period resolver (`resolvePeriodRange`), a shared `ReportResult` contract (`columns`/`rows`/`period`), a registry (`runReport`) dispatching by `ReportKey`, and a CSV exporter (`toCsv`) — matching ARCHITECTURE.md §15's own framing ("a single `reports` service exposes parameterized report definitions... rather than one bespoke export per module").
- **Three MVP report definitions** — Member, Attendance, Invitation — each composing pre-existing, already-RLS-scoped service functions (`members.listMembers`, `attendance.listSessions`+`getSessionRoster`+`listAttendanceStatuses`, `invitations.listInvitations`) rather than issuing a new raw query, so ARCHITECTURE §15's "an export can never contain data the requesting user could not otherwise see on-screen" holds by construction, not by a new permission check.
- **Excel and PDF rendering** (`apps/web`, via `exceljs` and `@react-pdf/renderer`) — see §2.2 for why these live in `apps/web` and not in `packages/services` alongside the CSV exporter.
- **The `/reports` web UI**: a report picker + period/filter form, an on-screen results table, and CSV/Excel/PDF download links, plus the `GET /reports/export` Route Handler that actually streams each format.
- **A "Reports" nav entry** with no permission gate — see §2.4.
- **A `joinedFrom`/`joinedTo` filter added to `members.listMembers`**, needed by the Member Report's period filtering, on the same RLS-scoped query every other `listMembers` caller already uses.

Explicitly deferred, named here rather than silently skipped:
- **The remaining eleven PRD §11 report subjects** (contribution, expense, vendor, inventory/asset, event, logistics, technical, uniform, discipline, HR, management) — PRD §15 itself calls the full fourteen-module engine a V2 feature, not MVP; 13.2 picks these up under this same Phase 13 authorization.
- **Management KPI dashboards** — PRD §15 names this as a *separate* V2 feature from the reporting engine itself, not a checkbox on this phase's list. A chart/analytics-style dashboard is a different UI concern from a filterable, exportable tabular report and is not attempted here.
- **Retrofitting the new PDF/Excel renderers onto letters, gate passes, or itineraries** — ARCHITECTURE §15 says PDF export "reuses the same rendering service as letters/gate passes/itineraries," and `render-pdf.tsx` is deliberately written as a generic tabular-report renderer so a future phase touching those modules has something to reuse (§2.3) — but this phase only wires it into Reports. Rewiring the other three modules is out of scope here.
- **A report *scheduler* or emailed/recurring report delivery** — not named anywhere in PRD §11/§15 for MVP; every report here is run on demand.

## 2. Architecture

### 2.1 Research finding that reshaped this phase's scope: no PDF/Excel/tabular-export infrastructure existed anywhere in this codebase

ARCHITECTURE §15's language ("PDF export reuses the same rendering service as letters/gate passes/itineraries," "Excel/CSV export uses a shared tabular-export utility") reads as if this phase only had to wire reports up to pre-existing shared infrastructure. Direct inspection before writing any code found otherwise: `itineraries/generate.ts`'s own doc comment states plainly that "no PDF/document-generation module exists yet for any phase to call into"; no package.json anywhere in the workspace depended on a PDF, Excel, or CSV library; `apps/edge-functions` remains an empty placeholder. `docs/PHASE_9_1.md` had already flagged this explicitly when descoping Financial Reports from Phase 9: "no reporting engine of any kind exists anywhere in this codebase yet... a general reporting engine is left for that dedicated phase" — this phase is that dedicated phase, and it had to build the engine from nothing, not merely surface one.

### 2.2 Module boundary: query/definition logic in `packages/services`; Excel/PDF rendering in `apps/web`, not alongside CSV

`toCsv` (dependency-free, hand-rolled RFC-4180-ish logic) stays in `packages/services/src/reports/export-csv.ts`, importable by both apps/web and, in principle, apps/mobile. `exceljs` and `@react-pdf/renderer` are real, heavy, Node-only libraries with zero use case on mobile — there is no server on the phone to render a PDF into, and no user-facing "export to Excel" gesture in a native app. Adding either dependency to `packages/services` (the package both web and mobile depend on) would mean shipping that dependency weight into the mobile bundle for a capability mobile never calls, directly against ARCHITECTURE §16 / spec §64's "minimal dependency footprint, no unnecessary dependencies." This is a deliberate, reasoned departure from a too-literal reading of §15's "a single `reports` service" — the part of that service every caller (web, mobile, a future scheduler) needs (the query/definition logic, `resolvePeriodRange`/`runReport`/the three definitions) is shared; the part only one caller needs (format-specific rendering) is not forced into the shared package just to satisfy the letter of "one service."

### 2.3 PDF renderer: `@react-pdf/renderer`, written generically, not a Reports-only component

ARCHITECTURE's stack table names either "a headless-Chromium or PDF-library based renderer" as acceptable. Headless Chromium was rejected specifically because of the well-known fragility/binary-size cost of shipping a full browser binary in a serverless deployment (this sandbox happens to have Chromium pre-installed for browsing/tooling use, but that is explicitly not a signal about what the deployed production runtime, e.g. Vercel, should carry). `@react-pdf/renderer` runs as a plain Node process with no browser dependency. `render-pdf.tsx`'s `ReportDocument` component takes a generic `{title, period, columns, rows}` shape (i.e. `ReportResult` itself) and renders a landscape A4 table — nothing Reports-specific is baked into it, so a future phase wiring PDF export into letters/gate passes/itineraries (§15's other three named consumers) has a renderer to reuse instead of standing up a second, divergent `@react-pdf/renderer` setup. This phase only calls it from the Reports export route; the other three modules are untouched.

### 2.4 No new permission — RLS is the real boundary, same as several other always-visible modules

The seed's full permission catalog (`supabase/seed/001_reference_data.sql`) has no `reports.*` entry, and none was added. Every report definition composes an existing, unchanged, RLS-governed service function; a caller can never see more through `/reports` than the live Members/Attendance/Invitations pages already show them, because it is the exact same query running under the exact same RLS session. The "Reports" nav group in `(erp)/layout.tsx` is therefore added with no `visible:` gate at all — the same "RLS is the real boundary, the nav is a convenience" shape already used for Uniforms, Technical Riders, Contributions, Calendar, and Media in that same file, not the permission-gated shape used for Discipline, Gate Passes, or Procurement.

### 2.5 Filter parsing centralized once, shared by the page and the export route

`(erp)/reports/filters.ts`'s `parseReportSearchParams` is the single function both `page.tsx` (rendering the on-screen table) and `export/route.ts` (streaming a download) call to turn raw query params into a validated `ReportKey` + `ReportFilters` — so a "Download CSV" link's query string, built from the exact same params the form just submitted, can never resolve to a different report/period than what's on screen. This mattered concretely during security review (§4): a validation gap in this one shared function is a gap in both callers at once, but so is a fix.

## 3. UI

- `(erp)/reports/page.tsx` — a GET-query-param-driven filter form (report picker, period type, year/month/quarter or custom from/to, an optional department and/or status narrowing depending on which report is selected), an on-screen results table, and three download links.
- `(erp)/reports/report-result-table.tsx` — a `"use client"` wrapper around `@ngc/ui`'s `Table` (itself client-only), matching every other module's own `*-table.tsx` pattern (e.g. `invitations/invitations-table.tsx`) — needed because a Server Component cannot pass a `render` function prop directly into a Client Component (see §4's first finding: an earlier version of this page did exactly that, and it crashed in production).
- `(erp)/reports/export/route.ts` — `GET /reports/export?report=...&period=...&format=csv|xlsx|pdf`, re-checks auth, re-parses the same filters, runs the report, renders the requested format, and streams it back with `Content-Disposition: attachment`.
- `(erp)/reports/render-xlsx.ts` / `render-pdf.tsx` — the Excel/PDF renderers described in §2.2/§2.3.
- `(erp)/layout.tsx` — a new "Reports" nav group (§2.4).

## 4. Security review

An adversarial review (Agent-dispatched, independent of the implementation) covered the RLS-scoping claims of all three report definitions, the export route's auth check, the `Content-Disposition`/filename construction, and both new export renderers. It read the actual RLS policies (not just the service code) for `members`, `attendance_sessions`, `attendance`, and `invitations`, and confirmed no report definition or the new `listMembers` date-range filter widens what any of those policies already permit. Three real issues were found and fixed before ship, none of them an RLS/authorization gap:

- **CSV formula-injection.** `toCsv`'s original `formatCell` only did RFC-4180 quoting, never neutralizing a leading `=`/`+`/`-`/`@`. Because `invitations.submitInvitation` is a public, unauthenticated, service-role-backed form with free-text organizer/event name fields (and because a member can edit their own name fields), a crafted string could reach a report cell and be evaluated as a formula the moment a staff member opened the exported CSV in Excel. Fixed by prefixing a leading `'` to any **string** cell (never a genuine `number` cell — a negative total is not itself a formula-injection risk) starting with one of those trigger characters, the standard OWASP CSV-injection mitigation. `exceljs`'s own `.xlsx` writer was checked and confirmed *not* vulnerable the same way — it classifies a plain JS string as a `String`-type cell regardless of its leading character, so it never emits an actual `<f>` formula node — so no equivalent change was needed there.
- **An unvalidated custom `from`/`to` reaching a downloaded filename.** The Invitations report's period filtering is an in-memory string comparison against `createdAt`, not a Postgres `date`-typed column the way Members/Attendance's filters are — so, unlike those two, nothing would have naturally rejected a malformed `from`/`to` before it flowed into `export/route.ts`'s `Content-Disposition` filename. Fixed by validating both against a strict `YYYY-MM-DD` pattern in the one shared `parseReportSearchParams` (§2.5), closing the gap for every caller at once rather than only for whichever report happened to hit it first.
- **A format-whitelist bypass via inherited `Object.prototype` keys.** The export route originally checked `format` against a plain object literal (`CONTENT_TYPES[format]`); a query string of `format=constructor` (or `toString`, `hasOwnProperty`, etc.) resolves to a truthy inherited value on a plain `{}`, defeating the intended whitelist and falling through to the PDF branch with a corrupted `Content-Type` header. Fixed by switching to a `Map`, which has no such inherited keys, and an explicit `.has()` check.
- **No SSRF/file-read vector was found in the PDF renderer** — it loads no external URL or file path, only the already-fetched `ReportResult` data.
- **No confidential-data leak from the always-visible nav entry** — cross-checked against how each source table's RLS is already documented; none of Members/Attendance/Invitations has a narrower policy than what the corresponding report definition assumes, and the Invitation Report in particular surfaces *fewer* columns than `listInvitations` already returns elsewhere (no `financial_information`, no contact fields), so it is narrower than existing, already-accepted invitation visibility, not wider.

A fourth, unrelated bug (not a security finding, but caught by the same verification pass) is worth naming here because it would have shipped broken without it: the first version of `page.tsx` passed `Table`'s `render` functions directly from the page's own Server Component into `Table` (a `"use client"` component) — Next.js's RSC boundary cannot serialize a plain function across that hop, and the page crashed with "Functions cannot be passed directly to Client Components" in a full production build, invisible at `typecheck`/`lint` time and only surfaced by an actual `next build` + Playwright run against the compiled output. Fixed by extracting `report-result-table.tsx` (§3), the same `"use client"`-wrapper pattern every other module's table already uses — this phase's own oversight of not following that established pattern from the start, caught by validation rather than by review.

## 5. Seed data changed this phase

None. No new table, column, permission, or RLS policy. `members.listMembers` gained two new **optional** filter parameters (`joinedFrom`/`joinedTo`), implemented as `.gte`/`.lte` on the already-RLS-governed `members` table — every existing caller that doesn't pass them is unaffected.

- **`pnpm --filter @ngc/web typecheck`** / **lint** (`next lint`) — both clean.
- **`pnpm --filter @ngc/web build`** (`next build`) — succeeds; `/reports` and `/reports/export` both compile and appear in the route manifest.
- **Full workspace regression**: `pnpm typecheck`/`pnpm lint` clean across all 8 packages, including `@ngc/mobile` — re-checked specifically because this phase's `members/list.ts`/`members/types.ts` changes are also depended on by Phase 12.3's mobile QR/event-assignments features. `pnpm --filter @ngc/mobile test` (14/14) and `npx expo export --platform android` both still succeed unchanged.
- **A new Playwright e2e spec, `e2e/reports.spec.ts`** (5 tests, all passing against a real running Next.js server + the mock Auth/PostgREST server, per this codebase's established e2e convention): a plain member sees the always-visible Reports nav link and runs the Member Report scoped to its period; the Attendance Report tallies presence correctly for the resolved period; the Invitation Report narrows by status as well as period; all three export links resolve to a 200 response with the correct `Content-Type` (exercised via `page.request` against the real Route Handler, not a simulated browser download); and an unauthenticated request to the export route is redirected to `/login` by middleware before ever reaching report data. This spec is what caught the RSC function-passing crash named in §4 — `typecheck`/`lint`/unit tests all passed with that bug still present, since it only manifests once React actually tries to serialize the page's props during a real render.
- **Security review**: an adversarial review (Agent-dispatched, independent of the implementation) — findings and all three fixes made before ship in §4.
- **Not verified**: real-world spreadsheet-application behavior of the CSV formula-injection fix (i.e. that Excel/Sheets/Numbers actually treat a leading `'` as "render as text," not just that this codebase's own test asserts the byte sequence is correct) — no spreadsheet application is available in this sandbox to open the exported file and confirm visually; the fix follows the standard, widely-documented OWASP mitigation, but is verified here by unit test of the string output, not by an executed spreadsheet-application check.
