# PHASE_12_3.md — Phase 12.3 Deliverable
## Neema Gospel Choir (NGC) ERP — Mobile: Contributions, Voting, Event Assignments, QR ID, Application Status

Phase 12 ("Mobile") concludes with this sub-phase. 12.1 built the app's foundation; 12.2 built the offline-capable Attendance module plus Leave/Events/Announcements/Notifications. 12.3 builds the remainder of ARCHITECTURE §9's mobile V1 list: Contributions (read/own), Voting, Event assignments, QR code display/scan, and Application status — the last named item mobile can reach without a native reimplementation of a service-role-gated flow (see §1).

## 1. Scope

In scope:
- **Contributions (read/own)**: a member's own contribution history plus a read-only list of currently active campaigns, both via existing, unchanged `contributions.listContributionsForMember`/`listCampaigns` (Phase 9.1). No "make a contribution" form — `contribution_records_write_finance` RLS (0014) requires `finance.contributions.manage`, so recording one is never a member self-service action on web either; this screen's own scope name ("read/own") is exactly what it does.
- **Voting**: a list of agenda items (`agendas.listAgendas`) and a detail screen showing the aggregate tally (`getAgendaResults`), the caller's own past vote if any (`getMyVote`), and a ballot form (`castVote`) when voting is open and unvoted — mirroring apps/web's own `[id]/page.tsx` exactly, including its explicit choice NOT to duplicate `eligible_voter_scope` eligibility checking client-side (§2.2).
- **Event assignments**: folded into the existing Calendar screen (`events.tsx`, from 12.2) as a "My assignments" section, rather than a new tab — see §2.1 for why, and a new read-only service function, `events.listEventAssignmentsForMember`, to back it.
- **QR code display/scan**: a "Member ID card" screen under Profile (`profile/qr.tsx`) — a member can show their own QR (encoding the pre-existing, never-before-surfaced `members.qr_token`) or scan someone else's to resolve a minimal identity view, via a new `members.getMemberByQrToken` function. See §2.3 for why this V1 build covers only this one of ARCHITECTURE §13's four named QR use cases.
- **Application status**: a "check your application status" link on the login screen that opens the existing public web page (`/join/continue`) in the device browser, rather than a native reimplementation — see §2.4 for why.

Explicitly deferred, named here rather than silently skipped:
- **Asset tag, Gate Pass, and Event/Attendance check-in QR** — all three tables already carry the same `qr_token` column (`0008`/`0010`/`0011`) this phase's Member ID card feature uses, but resolving them is an operations/security-desk workflow, not member self-service, and building three more staff-facing scan flows is out of this sub-phase's own framing. Named for whichever future phase actually owns operations-staff mobile tooling.
- **A leader/manager-facing "individual ballots" view for Voting on mobile** — web has one (`canManage && !agenda.isAnonymous`); mobile only builds the member self-service half, the same boundary 12.2 drew for Leave approvals.
- **A native "check your application status" form** — see §2.4; this remains a link-out, not a reimplementation, until (if ever) this codebase stands up its first Edge Function or an anon-callable `security definer` RPC to safely proxy that service-role-gated read from a client that must never hold the service-role key itself.
- **Tab bar information architecture** — now at 9 tabs (Dashboard, Attendance, Leave, Calendar, Giving, Vote, News, Alerts, Profile). 12.2 already named 7 as a V1 tradeoff; this phase makes it worse rather than solving it, and says so plainly rather than pretending otherwise (§2.1).

## 2. Architecture

### 2.1 Event assignments: folded into Calendar, not a new tab; a new, narrowly-scoped read function

`event_participants` (Phase 7.5) records who's assigned to which event, but no service function existed to read "my own assignments" specifically — every existing caller either wrote to it (`events.eligibility.manage`-gated) or read it as part of a bigger join this codebase doesn't have. `events.listEventAssignmentsForMember(client, memberId)` (new, `packages/services/src/events/list.ts`) does two flat queries — `event_participants` filtered by `member_id`, then `events` filtered by the resulting `event_id` set — mirroring this codebase's established "batch-resolve related rows with two queries, not a PostgREST embed" convention (`resolveDepartmentAndFamilyNames`). `event_participants_select_scoped` RLS (0008) is, as written, `member_id in (select id from members where user_id = auth.uid()) or auth.uid() is not null` — the second clause alone already lets any signed-in caller read every row for every member, so this new function inherits an already-broad read, it does not create one; see §4 for why this is named as a pre-existing item rather than fixed in this phase's own scope.

Rather than a tenth tab for a single read-only list, "My assignments" is a header section on the existing Calendar screen (`events.tsx`, 12.2) — the same screen already answers "what's happening," and "what am I assigned to" is a filtered view of exactly that, not a separate concept needing its own navigation destination.

### 2.2 Voting: zero new service code, client mirrors web's own "don't duplicate eligibility" choice

`agendas.listAgendas`/`getAgendaResults`/`getMyVote`/`castVote` (Phase 10.4) needed no changes. The mobile ballot screen (`voting/[id].tsx`) shows the vote form to any signed-in caller whenever `agenda.status === "open"` and the deadline hasn't passed and they haven't already voted — with no client-side re-derivation of `eligible_voter_scope`, `eligible_department_id`/`eligible_family_id`/`eligible_user_ids`, or the `leadership` → `management.agenda.manage` mapping (0034). This is a direct mirror of apps/web's own `[id]/page.tsx`, which states the same reasoning explicitly: a client-side-only eligibility check would be theater, not a boundary (0034's own doc comment); `votes_insert_self` RLS is the real gate, and an ineligible submission is refused there, surfaced to the mobile screen as the same `ServiceError` web shows inline.

### 2.3 QR: reusing four already-existing `qr_token` columns, not inventing a new token system

12.1 flagged QR as needing "real design work... before any code." The design work turned out to be discovery, not invention: `members`, `events`, `inventory`, and `gate_passes` each already carry `qr_token uuid not null default gen_random_uuid() unique` (migrations 0004/0008/0010/0011, each explicitly commented "opaque QR reference, resolved server-side (spec S59)"), mapped into their respective service types since the phases that built those modules — but with zero function anywhere that actually resolves one by scanning it. This phase builds exactly one such resolver, `members.getMemberByQrToken`, satisfying ARCHITECTURE §13's first named use case ("Member ID card, identity display, not raw auth") with no new table, migration, permission, or RLS policy: it is the same `members_select_scoped` policy `getMember` already relies on, just keyed by `qr_token` instead of `id` — so who a scan resolves anything for is identical to who could already read that member's profile via any other existing screen (self, `members.profiles.read_all` holders, or a department/family peer).

`getMemberByQrToken` deliberately returns `MemberSummary`, not the fuller `MemberDetail` a naive `select("*")` would produce — a security review of this phase (§4) flagged that the richer shape would pull a scanned member's national ID number, date of birth, contact details, and emergency-contact fields onto the *scanning* device for a UI that only ever renders name/number/department/status. Fixed by selecting only the ten columns the ID card view actually needs, before the row ever leaves Postgres — not an RLS gap (an authorized viewer could already read the full detail via `getMember`), but an avoidable data-minimization regression specific to a casual "show your badge" scan, caught and fixed before ship rather than shipped and revisited later.

The mobile screen (`profile/qr.tsx`) renders the caller's own `qrToken` as a QR image (`react-native-qrcode-svg` + `react-native-svg`) and scans others' via `expo-camera`'s `CameraView` barcode scanning. Asset tag, Gate Pass, and Event check-in resolution are NOT built — see §1's "explicitly deferred" list; this screen only ever attempts a `members` lookup, so scanning any of those other three tables' QR codes here correctly (if unhelpfully) reports "not a recognized NGC member ID" rather than silently mis-resolving or crashing.

### 2.4 Application status: a link-out, not a native reimplementation — a real architectural boundary, not laziness

`applications.getApplicationForApplicant`'s own doc comment (`packages/services/src/applications/token.ts`) states the constraint precisely: an applicant has no Supabase Auth session at all, so `applications` has intentionally NO anon/authenticated RLS policy — every applicant-facing read runs through the RLS-**bypassing** service-role client, which apps/web reaches via a Next.js Server Action (`apps/web/app/join/actions.ts`) running server-side. Mobile has no server of its own; it is a pure client speaking directly to Supabase. Shipping the service-role key inside a native app bundle would hand out a full-database-bypass secret in a decompilable artifact — not a hardening gap to fix later, a categorically wrong thing to ever do. Building a safe alternative (an Edge Function, or a new `security definer` Postgres RPC callable by `anon` that re-implements the same token-hash-plus-contact verification `loadAndVerify` already does) is real, separate infrastructure work — `apps/edge-functions` is still a placeholder in this codebase, and adding its first real function is a bigger change than this one login-screen link deserves to smuggle in unannounced. The login screen instead opens `${EXPO_PUBLIC_APP_URL}/join/continue` (a new env var, defaulting to the production app URL if unset, since it's a public URL, not a secret) in the device browser — the applicant reaches the exact same, already-reviewed verification flow web already serves, just not reimplemented natively. Named explicitly as the deliberate boundary it is, not glossed over as done.

- `app/(app)/voting/index.tsx` / `[id].tsx` — agenda list with status; detail screen with tally, the caller's own vote or a ballot form, and the same "checked at the database level" disclaimer web shows.

- `app/(app)/profile/qr.tsx` — a two-mode screen: "My ID" (own QR) and "Scan" (camera scan → resolved identity card or "not recognized").
- `app/(app)/profile/index.tsx` (extended) — a "My ID / Scan a member ID" button linking to the new `qr` screen, shown only if the caller has a linked member record.
- `app/(auth)/login.tsx` (extended) — a "Check your application status" link opening the web app's existing public status page.
- Tab bar (`app/(app)/_layout.tsx`) — two new tabs, "Giving" (Contributions) and "Vote" (Voting), bringing the total to nine.

## 4. Security review

An adversarial review (Agent-dispatched, independent of the implementation) covered the new QR resolver and screen, `listEventAssignmentsForMember`, the Contributions/Voting screens' trust of caller-supplied identifiers, and the login link-out. Findings:

- **One real issue found and fixed before ship**: `getMemberByQrToken` originally returned the full `MemberDetail` shape (national ID number, date of birth, contact details, address, emergency contact) to the scanning device for a UI that never displays any of it. Not a new RLS gap — the scanning caller could already read all of it via `getMember` if authorized — but a genuine data-minimization regression specific to this feature. Fixed by narrowing the query to exactly the columns the ID-card view needs (§2.3), before ship, not flagged-and-deferred.
- **The QR feature otherwise introduces no new authorization surface.** Resolving by `qr_token` uses the identical `members_select_scoped` RLS predicate `getMember` (by `id`) already relies on — verified by re-reading the policy, not assumed. The non-rotating nature of `qr_token` (a permanent UUID, not a short-lived rotating one) was assessed and found not to be a meaningful risk here specifically: it only ever enables a *read* of the same profile data an authorized viewer could already see through any other screen; no write path in this schema keys off `qr_token`, so there is nothing to "impersonate" beyond that read. Enumeration is infeasible (a 122-bit random UUID keyspace, plus a generic `null` for both "no such token" and "found but RLS-denied," the same no-oracle shape `applications.getApplicationForApplicant` already uses).
- **`event_participants_select_scoped`'s own breadth is pre-existing, not introduced by this phase — named, not fixed here.** The policy's `... or auth.uid() is not null` clause already lets any signed-in user read every `event_participants` row for every member, regardless of whose `member_id` is queried. `listEventAssignmentsForMember` inherits this rather than creating it, and the only caller today (the mobile Calendar screen) only ever passes the signed-in user's own member id — but the function itself has no server-side self-scoping, so a hypothetical future caller passing an arbitrary `memberId` would legitimately get another member's full assignment history. Named as an open item (§7) for whoever next touches this policy, consistent with this phase's own precedent (12.2's `recorded_by`/audit-trigger note) of not silently expanding scope to fix a pre-existing gap this sub-phase merely surfaced rather than introduced.
- **Voting and Contributions confirmed not spoofable.** `castVote` is always called with `voterId: user.id` (the caller's own signed-in id, never a route param or form field), and `votes_insert_self` RLS requires `voter_id = auth.uid()` regardless of what a compromised client might send. `listContributionsForMember`/`listCampaigns` are unchanged, already-reviewed (Phase 9.1) functions; no new write path was added.
- **The Application-status link-out is the correct architectural choice, not a shortcut.** `EXPO_PUBLIC_APP_URL` is a build-time env var, not attacker-controlled at runtime, so there is no injection vector in constructing the URL; deferring to the one place that legitimately holds the service-role client (the Next.js Server Action) rather than attempting a native reimplementation is exactly the boundary §2.4 describes. Noted only as a low-severity config-integrity point: if that env var were ever misconfigured to a non-organization domain, the link would silently open an arbitrary URL — a deployment-configuration risk, not a code vulnerability.

## 5. Seed data changed this phase

None. No new table, column, permission, or RLS policy. Every read this phase's screens perform relies on RLS policies that already existed (`members_select_scoped`, `event_participants_select_scoped`, `contribution_records_select_scoped`, `votes_insert_self`/`votes_select_own_or_admin`, `agendas_select_authenticated`) — this phase only adds two new, narrowly-scoped service functions (`members.getMemberByQrToken`, `events.listEventAssignmentsForMember`) that call existing tables through existing policies.

## 7. Open issues / deferred, not overlooked

- **`event_participants_select_scoped` RLS is broader than any current caller needs** — any signed-in user can read any member's event assignments; not exploited by this phase's own (self-only) caller, but worth tightening (e.g. to mirror `contribution_records_select_scoped`'s own self-or-permission shape) the next time this policy is touched. See §4.
- **Asset tag, Gate Pass, and Event/Attendance check-in QR resolution** — the `qr_token` columns exist; no resolver or scan UI was built for them this phase, deliberately (§1) — an operations/security-desk mobile tool, not member self-service.
- **No native "Application status" flow** — remains a link-out to the web page pending either this codebase's first Edge Function or a new anon-callable `security definer` RPC (§2.4).
- **A leader/manager ballots view on mobile Voting** — web-only in V1, same boundary as Leave's approvals queue (12.2).
- **The tab bar is now nine tabs** — a real usability concern on smaller phones, named plainly rather than solved; a future phase should design a proper information architecture (a "More" tab, a drawer, or grouping) rather than this phase inventing one under momentum.
- **No on-device verification of the camera/QR-scanning flow** — same sandbox constraint every mobile phase has named; `expo export`'s bundle-only verification does not exercise the actual camera permission prompt or barcode detection.
- **Every other 12.1 open item not yet revisited** (component/rendering-level tests, EAS registration, app icon/splash, Documents/Constitution read screens) — unchanged since 12.1/12.2, not reintroduced or silently dropped by this phase.
