# PHASE_12_2.md — Phase 12.2 Deliverable
## Neema Gospel Choir (NGC) ERP — Mobile: Member Self-Service

Phase 12 ("Mobile") is decomposed into sub-phases (see `docs/PHASE_12_1.md`'s own opening note) — 12.1 built the app's foundation (navigation shell, auth, theme, Dashboard/Profile). This sub-phase, 12.2, builds the member self-service modules ARCHITECTURE §9/§18 name for V1 mobile: Attendance (including offline capture — the one genuinely new piece of business logic this phase adds), Leave, Events/Calendar, Announcements, and Notifications. QR codes, voting, contributions (read/own), event assignments, and application status remain 12.3, per the same scope split 12.1 already named.

## 1. Scope

In scope:
- **Attendance**: a member-facing summary (reusing `attendance.getMemberAttendanceSummary`, unchanged, from 12.1's Dashboard) plus, for anyone who already holds department-write scope on the web (`attendance.records.manage` or a department-scoped role), a "take attendance" flow that is **offline-first**: every status tap is queued locally before any network attempt, and syncs via a new idempotency-key-based service function — see §2.1.
- **Leave**: a member's own leave request history (`leave.listLeaveRequests({ memberId })`) and a new-request form (`leave.createLeaveRequest`), both unchanged service functions from Phase 7.4/6.
- **Events/Calendar**: a read-only agenda for the current calendar month via `calendar.listCalendarItems`, unchanged from Phase 11's aggregation of events + attendance sessions + contribution deadlines.
- **Announcements**: a read-only list/detail view via `announcements.listAnnouncements`/`getAnnouncement`, unchanged from Phase 10.1.
- **Notifications**: a member's own inbox via `notifications.listMyNotifications`/`markNotificationRead`, unchanged from Phase 10.1.
- **`@tanstack/react-query`** newly wired into mobile (`src/lib/query-client.ts`, `<QueryClientProvider>` in the root layout) — ARCHITECTURE's own tech-stack table names this as the shared web+mobile data-fetching layer; this phase is mobile's first actual use of it (12.1's Dashboard used a raw `useEffect` fetch instead).
- **The mobile tab bar widened** from 12.1's two tabs (Dashboard, Profile) to seven (Dashboard, Attendance, Leave, Calendar, News, Alerts, Profile) — see §2.4 for why this is named as an open item, not a finished piece of navigation IA.

Explicitly deferred, named here rather than silently skipped:
- **A leader/manager-facing approvals queue for Leave** — `listLeaveRequests` also serves a scoped "everyone I can see" view (its own `leave_requests_select_scoped` RLS), which web already exposes as an approvals UI; this phase only builds the member self-service half on mobile. Same "not every manage-side flow gets V1 mobile parity" boundary 12.1 drew for attendance-session creation.
- **Calendar month navigation** — always shows the current calendar month; no prev/next control yet.
- **A native date picker for Leave's start/end dates** — plain `YYYY-MM-DD` text fields, to avoid pulling in a new native dependency (`@react-native-community/datetimepicker`) for a V1 form.
- **A disk-persisted React Query cache** (e.g. `@tanstack/query-async-storage-persister`) — ARCHITECTURE §18 calls for an "offline/last-updated indicator on read-mostly data"; this phase wires React Query itself but not that persister, so a cold app launch while offline still shows an empty/loading state for Calendar, Announcements, and Notifications rather than the last-known data with a staleness indicator. Attendance is the one screen ARCHITECTURE actually requires to work offline (a WRITE path, §18's explicit target), and that is fully built (§2.1); this gap is about read-side staleness UX only.
- **QR codes, voting, contributions (read/own), event assignments, application status, Documents/Constitution (read)** — 12.3, per 12.1's own scope split (Documents in particular still has no service layer anywhere in this codebase — a gap named again here, unchanged since Phase 9.2).

## 2. Architecture

### 2.1 Offline attendance capture: idempotency-key upsert, never a silent overwrite

**Who can take attendance, and why this isn't member self-check-in.** `attendance_write_scoped` RLS (`0006_attendance_leave.sql`) requires `attendance.records.manage` or the caller's own department scope covering the session's department — there is no member-self carve-out, so a plain member cannot write an attendance row even for themselves. ARCHITECTURE §18's "offline attendance capture" is therefore for whoever *takes* attendance (a department leader, or an `attendance.records.manage` holder), not a member self-check-in feature. `apps/mobile/app/(app)/attendance/index.tsx`'s `useCanManageAttendance()` mirrors apps/web's own identical client-side gate (`apps/web/app/(erp)/attendance/page.tsx`) exactly — a UX-only gate; RLS is what actually enforces it either way (confirmed in §4).

**The new service function.** `packages/services/src/attendance/sync-offline.ts` exports `syncOfflineAttendance(client, input)`, taking a required `clientIdempotencyKey` (distinct from the existing online-only `recordAttendance`) and returning one of four outcomes:
- `synced` — no existing row for `(sessionId, memberId)`; inserted with `recorded_via: "mobile"`.
- `already_synced` — an existing row's own `client_idempotency_key` matches the input's; a no-op, not a duplicate insert. This is what makes a retried flush of the same queued tap safe.
- `conflict` — an existing row exists with a *different* (or null) idempotency key — i.e. someone else already recorded this member for this session. The existing row's state is returned; it is **never overwritten**.
- `session_not_found` — the session no longer exists (`attendance_sessions` has no "cancelled" status column; a session is either present or hard-deleted, cascading its `attendance` rows). This is the concrete form ARCHITECTURE §18's "a conflicting server-side state (e.g. session cancelled meanwhile)" takes in this schema.

This directly satisfies ARCHITECTURE §18's three explicit requirements — idempotent retry-safety, no silent duplication, conflicts surfaced as resolvable rather than silently overwritten — using the pre-existing `attendance.client_idempotency_key` + `uq_attendance_idempotency` schema hook (shipped in Phase 4/7.3, explicitly commented "for offline mobile capture / sync conflict resolution (ARCHITECTURE S18)" and left unused until now). Fully unit-tested: `sync-offline.test.ts`, 6 tests covering all four outcomes plus input validation (blank idempotency key, unrecognized status code) — `pnpm --filter @ngc/services test` is 396/396 (390 pre-existing + 6 new).

**The mobile queue.** `apps/mobile/src/lib/attendance-queue-core.ts` is pure, dependency-injected queue logic (`enqueue`/`getQueue`/`flush`) with zero `react-native`/Expo imports — same testability pattern 12.1 established for `chunked-storage.ts` vs `secure-storage.ts` (importing a native module transitively pulls in `react-native`'s own Flow-syntax source, which `tsx --test`'s esbuild transform cannot parse). `attendance-queue.ts` is the thin real wiring: `AsyncStorage`-backed persistence under key `ngc-mobile:attendance-offline-queue`, and `attendance.syncOfflineAttendance` as the sync function. `flush()`'s contract mirrors the service function's own four outcomes exactly: `synced`/`already_synced` are removed from the queue as resolved; `conflict`/`session_not_found` are also removed (resolved, but surfaced to the UI rather than retried forever); anything else that throws (most commonly: still offline) stays queued for the next flush attempt. `attendance-queue-core.test.ts` — 6 tests, all passing, covering exactly this bucketing.

**Why AsyncStorage here, unlike the session-token adapter.** `expo-secure-store` (12.1's choice for the Supabase session, §2.2 of PHASE_12_1.md) was rejected for this queue: a queued attendance record (`sessionId`, `memberId`, `statusCode`, `notes`, `recordedBy`) carries no credential, unlike a session JWT, so it doesn't need Keychain/Keystore-level protection — explicit in-code comment distinguishes this from the security-motivated choice made for session storage, so a future reader doesn't mistake this for an inconsistency. (Revisited, not contradicted, by §4's forward-looking note on `notes`.)

**The screen.** `apps/mobile/app/(app)/attendance/[id].tsx` is deliberately offline-first, not "try online, fall back to queue on failure": every tap writes to the durable local queue *first*, then attempts an immediate flush — so a record is never at risk of being lost to an app crash or kill between the tap and a slow/failed network call. Local `pendingByMember`/`conflictsByMember` state overlays the server-sourced roster query, since a just-queued-but-not-yet-synced tap needs its own optimistic indicator (the roster query itself only reflects confirmed server state).

### 2.2 React Query: mobile's first real use

`src/lib/query-client.ts` configures `staleTime: 60_000, retry: 1` and wraps the whole app (`app/_layout.tsx`) in `<QueryClientProvider>`. Every new 12.2 screen uses `useQuery`/`useQueryClient` instead of 12.1 Dashboard's raw `useEffect` fetch. `queryClient.invalidateQueries` is used after a successful attendance sync and after a Leave request submission, so a screen reflects a just-written change without a manual pull-to-refresh.

### 2.3 Read-only screens: unchanged service calls, RLS trusted exactly as web trusts it

Events/Calendar, Announcements, and Notifications add no new service-layer code — every screen calls an existing, unchanged `packages/services` function and trusts that function's own RLS to scope results correctly, the same pattern every read screen in this codebase (web or mobile) has followed since Phase 7.1. The one piece of mobile-specific judgment: `events.tsx` only makes `attendance_session`-type calendar items pressable (`router.push(item.href)`, and `listCalendarItems`'s own `href` for that type is `/attendance/:id` — a route this mobile app actually has). `event`/`contribution_deadline` items' `href`s (`/events/:id`, `/contributions/:id`) point at web-only routes not yet built on mobile (12.3+), so those rows are informational only rather than a dead-end tap.

### 2.4 Tab bar: seven tabs, named as a V1 tradeoff

`app/(app)/_layout.tsx` now exposes Dashboard, Attendance, Leave, Calendar ("events" route), News ("announcements" route), Alerts ("notifications" route), and Profile. Seven tabs is dense for a bottom tab bar, especially on smaller phones; this phase accepts it for V1 rather than introducing a "More" overflow tab or a drawer, both of which are real navigation-IA decisions ARCHITECTURE doesn't prescribe and this phase's scope (build the screens named in §9/§18) doesn't require resolving. Named as an open item (§7), not silently shipped as the intended final IA.

## 3. UI

- `app/(app)/attendance/index.tsx` — the caller's own attendance summary; for a manager/leader, a list of sessions (tap to take attendance); a banner showing how many records are queued offline, refreshed on pull-to-refresh and on mount (which also attempts a flush).
- `app/(app)/attendance/[id].tsx` — the roster for one session, with a pill-button status selector per member; shows "Syncing…" for a locally-queued-not-yet-confirmed tap, and a conflict message (with the server's actual recorded status) if a sync attempt surfaces one.
- `app/(app)/leave/index.tsx` — the caller's own leave request history with a status badge (pending/approved/rejected/cancelled), and a button to `leave/new.tsx`.
- `app/(app)/leave/new.tsx` — leave type picker, start/end date text fields, reason field; submits via `leave.createLeaveRequest`.
- `app/(app)/announcements/index.tsx` / `[id].tsx` — a read-only list (title, message excerpt, priority) and detail view (full message, optional image).
- `app/(app)/events.tsx` — a read-only merged agenda for the current month.
- `app/(app)/notifications.tsx` — the caller's own inbox; tapping an unread notification marks it read.
- `src/components/Card.tsx` — a small themed container (surface-raised background, hairline border, rounded corners) shared across every new screen above, matching `packages/ui`'s own `<Card>` visual role (not a port — that's a React DOM component, unusable in React Native).

## 4. Security review

An adversarial review (Agent-dispatched, independent of the implementation) covered the new `syncOfflineAttendance` service function, the mobile offline queue, and every new self-service screen's RLS assumptions. Findings:

- **`recorded_by` is client-supplied and unverified, and `attendance` has no audit trigger despite its own migration comment claiming one — pre-existing, not introduced by this phase, named as an open item (§7).** Both the existing `recordAttendance` and the new `syncOfflineAttendance` insert `recorded_by` verbatim with no check that it equals `auth.uid()`, and `attendance_write_scoped` RLS has no `with check` constraining that column; separately, `public.attendance` is not among the tables `0021_audit_triggers.sql` actually instruments, despite `0006`'s own table comment claiming "additionally written to audit_logs via trigger." Together this means there is currently no independent record of who truly captured a record if `recorded_by` were misrepresented by a caller who already holds write scope. This affects both the old and new write path equally — not something 12.2's mobile code introduced — so it is named for a future phase to fix (adding `attendance` to the audit-trigger list, and/or a `with check (recorded_by = auth.uid())` clause) rather than fixed here, out of this sub-phase's own scope.
- **A theoretical TOCTOU on a brand-new `(session_id, member_id)` pair — not exploitable as a duplicate-write, confirmed self-healing.** Two concurrent `syncOfflineAttendance` calls with different idempotency keys targeting a never-before-written pair could both pass the "no existing row" check; the table's unconditional `unique (session_id, member_id)` constraint prevents an actual duplicate row regardless, and the losing call's raw Postgres error is treated by the mobile queue as a transient failure (`stillQueued`, retried) — on retry, the existing-row check now finds the winner's row and correctly returns `conflict`. The "never silently overwritten" guarantee holds; the only cost is a one-retry delay before the conflict is surfaced.
- **The mobile `canManage` gate is UX-only, and is not exploitable given RLS.** Deep-linking directly to `/attendance/[id]` as a plain member yields at most a roster scoped to the caller's own row (`members_select_scoped`/`attendance_sessions_select_scoped`) and no ability to write (`attendance_write_scoped` has no member-self carve-out) — confirmed by re-reading both policies, not assumed.
- **Leave and Notifications self-scoping confirmed not spoofable.** `leave_requests_insert_self` RLS (`member_id in (select id from members where user_id = auth.uid())`) prevents `leave/new.tsx` from submitting on another member's behalf regardless of what `memberId` a compromised client sent. `notifications_update_own_read` RLS (`recipient_user_id = auth.uid()`, no permission-based bypass) prevents `markNotificationRead` from touching another user's notification; a mismatched id fails closed (0 rows, `.single()` errors) rather than leaking existence via a different error shape.
- **An initial Announcements finding, investigated and confirmed NOT a bug — deliberate, already-documented, already-reviewed design, not reversed by this phase.** The review first flagged that `announcements_select_published` RLS never filters by `target_audience`/`target_department_id`/`target_family_id`/`target_user_ids`, so a "leadership"- or "specific_users"-targeted announcement is readable by any signed-in member once live. On checking `docs/PHASE_10_1.md` §2.2, this is explicit, intentional, and was itself security-reviewed at the time: "the audience fields describe who an announcement is *intended for*, they do not *restrict* who can see it — the same 'any signed-in user reads everything' transparency baseline this codebase has used since Invitations (7.5) for tables with no per-row confidentiality requirement." Reversing that now, on this phase's own initiative, would silently overturn a previously reasoned and reviewed cross-phase decision rather than fix an actual regression — so no migration was written. This is recorded here specifically so a *future* reviewer re-discovering the same pattern finds this note before re-litigating it a third time.
- **Forward-looking note, not a defect today**: the offline attendance queue's AsyncStorage-is-fine-here reasoning (§2.1) depends on queued data carrying no sensitive free text. Today's queue only carries `notes: null` in practice (the mobile "take attendance" screen never sets a note). If a future phase extends this same queue pattern to carry genuinely sensitive free text (e.g. a Leave `reason`, which can describe health/family circumstances), the "no credential = AsyncStorage is fine" reasoning would need to be revisited at that point, not silently assumed to still hold.
