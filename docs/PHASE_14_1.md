# PHASE_14_1.md — Phase 14.1 Deliverable
## Neema Gospel Choir (NGC) ERP — QA: Correctness & Security Gap Remediation

Phase 14 ("QA") has no PRD-defined scope — `docs/ARCHITECTURE.md` §19 names it only as a roadmap position ("13. Reporting → 14. QA → 15. Deployment"), subject to the same generic Development Control Rule as every other phase, with no module list or checklist the way Phases 7–13 each had. Given that, 14.1 scopes itself around a concrete, bounded body of work: the previously-flagged, **not accepted-by-design** correctness/security gaps that accumulated across Phases 7–13's own "Open issues / deferred, not overlooked" sections, each already named explicitly in its own phase doc rather than discovered fresh here. This sub-phase fixes them; later 14.x sub-phases (CI/test hardening, accessibility, a capstone regression + review pass) continue under this same Phase 14 authorization.

## 1. Scope

In scope — six previously-named, not-yet-fixed gaps, each verified against a real local Postgres 16 instance before and after its fix (not just unit/e2e tests, which run against a hand-written mock server that does not enforce RLS at all — see §4):

1. **The recurring "workflow bypass via direct REST write" pattern** (named independently in docs/PHASE_9_2.md and docs/PHASE_9_3.md, and found on this phase's own inspection to also be true, unflagged until now, of Invitations and Gate Pass): any holder of a flat RLS permission (`finance.expenses.manage`/`.approve`, `inventory.gate_passes.manage`/`person_responsible_id`, `events.invitations.manage`) could set `status = 'approved'`/`'rejected'`/`'declined'` directly on `expense_requests`/`gate_passes`/`invitations`, skipping every configured approver, because the service layer's own post-decision "sync the record's status" write was gated only by that flat permission, with nothing tying it to whether `record_workflow_decision` had actually, correctly advanced the workflow. Separately, `workflow_instances` itself could be directly overwritten by any `management.approvals.manage` holder, contradicting `record_workflow_decision`'s own doc comment ("administrative override... not step impersonation").
2. **Procurement's own status-machine integrity** (named in docs/PHASE_9_3.md as "the same class of gap"): a `finance.procurement.manage` holder could jump `procurement_requests.status` directly from `pending` to `purchased`, or resurrect a terminal `purchased`/`cancelled` request, skipping the intermediate business logic (`purchase.ts`/`vendor.ts`/`cancel.ts`) entirely.
3. **`playlists.shared_with_roles`** (docs/PHASE_8_4.md §7): stored and editable since Phase 8.4, never enforced by `playlists_select_scoped`.
4. **`event_participants_select_scoped`** (docs/PHASE_12_3.md §7): a dead `or auth.uid() is not null` branch made every row readable by any signed-in user, broader than any shipped caller needs.
5. **The attendance audit-trail bug** (docs/PHASE_12_2.md §7): `public.attendance`'s own table comment claims every change is "written to audit_logs via trigger," but the table was never actually attached to 0021's audit-trigger list — every attendance change has been silently unaudited since Phase 7.3, contrary to spec S41 and the table's own documentation.
6. **Standing RPC EXECUTE grants** (named in 0033's own comment, repeated in docs/PHASE_10_2.md §7): every SECURITY DEFINER RPC in this schema left Postgres's default PUBLIC-EXECUTE-on-create grant unrevoked.

Explicitly deferred, named here rather than silently skipped (candidates for a later 14.x sub-phase or a dedicated future phase, not overlooked):

- **Trips/Itineraries' broader-than-PRD read scoping** (docs/PHASE_8_5.md §7 — PRD names Choir Member/Department Leader as "Read (assigned trip)" only, but both tables are readable by any signed-in user today). Not fixed this sub-phase: doing so correctly requires either a new `assigned_member_ids`-style column on `trips` itself (today only `itineraries.assigned_member_ids` exists) or re-deriving trip-level visibility from itinerary assignment — a real schema/product decision, not a same-shape RLS-policy edit like the six items above.
- **Four permission-model "completeness" gaps** naming a PRD-described entitlement with no supporting permission code or grant at all (`finance.expenses.read` for HR; Department Leader/Finance Manager read access to Inventory/Assets; a Department Leader's own-department Contributions summary read; a Department Leader's "create own department" Announcements entitlement — docs/PHASE_8_1.md, PHASE_9_1.md, PHASE_9_2.md, PHASE_10_1.md respectively). These are under-permissive gaps (missing access, not leaked access) and each requires a real product decision about a new permission code and its exact department/role scoping, not a bug fix — deliberately kept out of a security-hardening sub-phase.
- Every other item in Phases 7–13's own "deferred, confirmed-by-design" lists (TOCTOU races, no member/vendor/event picker with name search, no PDF export for gate passes/itineraries, no repair-tracking workflow, etc.) — unchanged, still exactly as those phases' own docs described them.

## 2. Architecture

### 2.1 Why this is four small, targeted migrations rather than one broad rewrite

Each of the six gaps above has an independent root cause and an independent, minimal fix — bundling them into a single sprawling migration would make each one harder to review and to roll back individually if needed. `supabase/migrations/0036_workflow_direct_write_hardening.sql` groups the two migration-integrity items (workflow bypass + procurement) since they share the same "guard a status column against a direct write" shape; `0037_playlists_sharing_and_event_participants_scope.sql` groups the two read-scoping fixes; `0038_attendance_audit_and_recorded_by_guard.sql` and `0039_rpc_execute_hardening.sql` are each their own single-purpose migration.

### 2.2 The workflow-bypass fix, in detail

The vulnerable shape: `expenses/workflow.ts`, `gate-passes/workflow.ts`, and `invitations/approval.ts` each call the SECURITY DEFINER `record_workflow_decision` RPC (which correctly re-verifies the caller matches the *current* step's required role/user) to advance `workflow_instances`, then separately issue a plain client `.update({status: ...})` on the underlying record to sync its own status column — a write gated only by a flat RLS permission check, unconnected to whether the workflow was actually, legitimately advanced.

The fix has two parts. First, `workflow_instances_write_service` (previously `for all`) is replaced with an INSERT-only policy — the only legitimate direct client write to this table was already `workflow.startWorkflow()`'s insert; every advance goes through `record_workflow_decision`, whose own internal writes are unaffected by this narrowing (a SECURITY DEFINER function executes as its owner, which bypasses RLS, the same way `write_audit_log()` already does). This closes the "overwrite `workflow_instances` directly" half of the gap — verified against live Postgres: a `management.approvals.manage` holder's direct `UPDATE` on a `workflow_instances` row now affects 0 rows.

Second, a new generic BEFORE UPDATE trigger function, `guard_workflow_governed_status_change()` (parameterized via `TG_ARGV`, reused across `invitations`, `expense_requests`, and `gate_passes`), intervenes only for the one specific transition each table's own service-layer code performs immediately after a workflow reaches its final decision. It re-reads `workflow_instances` (SECURITY DEFINER, bypassing the calling role's own RLS visibility into that table) for the exact `record_type`/`record_id`, and requires it to already reflect the corresponding outcome before allowing the sync-write through; any other direct exit from the guarded status is rejected outright unless it's on a small, explicit "always allowed" allowlist of real, separately-gated non-approval exits (today exactly one: invitations' own `cancelInvitation`, `pending_management_approval` → `cancelled`). This was deliberately NOT done by moving the status-sync logic into the RPC itself and revoking column-level UPDATE privileges — Supabase-JS's `.rpc()` call and the following `.update()` call are separate HTTP requests/transactions, so a session-local "ticket" (a GUC set inside the RPC, checked by the trigger) would not survive between them; re-reading the already-committed `workflow_instances` row instead needs no such cross-request state, and leaves every side effect (e.g. `invitations.approval.ts`'s `createEventFromInvitation` call) exactly where it already was, in TypeScript.

This function went through two real revisions during this sub-phase's own validation, both caught before ship rather than after:

- **Caught by manual Postgres testing**: an earlier draft only intervened when the new status was one of the guarded outcomes, leaving every OTHER direct exit from the guarded status completely unguarded — a gate pass's `person_responsible_id` (who needs no special permission at all) could jump `pending_approval` straight to `checked_out`, skipping approval entirely rather than forging its outcome. Fixed by guarding every exit from the guarded status, not just the two forgeable ones.
- **Caught by an independent adversarial security review** (dispatched as part of this sub-phase, before ship — see §4): the revised trigger compared the new status against `workflow_instances.status` for exact equality, which is wrong for invitations specifically — `invitations.status`'s rejection value is `'declined'`, but `workflow_instances.status` only ever uses `'rejected'`. The two vocabularies never matching would have unconditionally blocked every legitimate invitation rejection sync, permanently stuck at `pending_management_approval` with no recovery path (the workflow instance itself would already be terminal). Fixed by making the guarded "to" list a set of `new_status:expected_workflow_instances_status` pairs rather than assuming identical spelling, and re-verified end-to-end against live Postgres through the real `record_workflow_decision` RPC (not just a hand-seeded workflow instance row).

Procurement's own gap has a different shape — it has no `workflow_instances` row at all (a sequence of Finance-driven operational steps, not a peer-approval chain) — so it's fixed with a plain state-machine transition-validity trigger (`pending → vendor_selected|cancelled → purchased|cancelled`), independent of any workflow instance.

### 2.3 The read-scoping and audit fixes

`playlists.shared_with_roles` is enforced by reusing the exact role-array-membership RLS pattern Phase 11's own security review already shipped for `media_links.shared_with_roles` (0035) — purely additive, granting visibility to specified roles that previously had none via this column. `event_participants_select_scoped` is narrowed to "own member row, or `events.eligibility.manage` holder" after confirming (by inspecting every caller in both `packages/services` and `apps/web`/`apps/mobile`) that every existing reader already filters to the caller's own `member_id` — narrowing changes nothing for any shipped feature.

Attendance gets two independent fixes: `attendance`/`attendance_sessions` are added to the audit-trigger list (matching the table's own pre-existing, previously-false claim), and `attendance_write_scoped` gains a `WITH CHECK (recorded_by = auth.uid() ...)` clause — confirmed safe by checking every production caller (`apps/web/app/(erp)/attendance/actions.ts`, `apps/mobile/app/(app)/attendance/[id].tsx`) already passes the signed-in user's own id as `recordedBy`.

### 2.4 RPC EXECUTE hardening

`revoke execute ... from public` plus an explicit `grant ... to authenticated` on the six pre-existing SECURITY DEFINER RPCs (`find_member_by_number_for_discipline`, `apply_disciplinary_membership_status`, `record_workflow_decision`, `start_gate_pass_workflow`, `start_expense_request_workflow`, `send_notification`) — defense-in-depth, since every one of these already re-verifies the caller's own permission/role internally. Verified against live Postgres that PUBLIC's own grant is genuinely gone (`has_function_privilege('public', ..., 'EXECUTE')` returns `false` post-migration); `anon` still shows as able to execute in THIS sandbox only because of 0024's local-dev-only `alter default privileges ... grant execute on functions to anon, authenticated`, a statement explicitly guarded to never run against a real Supabase project (confirmed by re-reading 0024's own guard) — not a regression of this migration's intent in production, and the identical caveat 0033's own comment already documented for this exact gap.

None. This sub-phase is entirely database-layer (RLS policies, triggers, grants) — no new pages, no new service-layer-facing behavior change for any legitimate caller. ## 4. Security review

Every fix in this sub-phase was verified twice: once by hand against a real local Postgres 16 instance (not the Playwright e2e suite's mock Auth/PostgREST server, which — per its own doc comment — does not replicate RLS at all and so cannot validate any of these changes), and once by an independent, adversarial security review (Agent-dispatched, given no context from the implementation) that read every new migration's SQL directly rather than trusting a summary of intent.

The review caught one real, would-have-shipped regression before commit: the invitations `'declined'` vs. `workflow_instances.status`'s `'rejected'` vocabulary mismatch described in §2.2, which would have permanently blocked every legitimate invitation rejection. It also independently confirmed: the guard trigger's SECURITY DEFINER bypass of RLS on `workflow_instances` is safe and necessary (it never returns instance data to the client, only a boolean-shaped exception); the `unique (record_type, record_id)` constraint on `workflow_instances` (0019) is real and enforced, so the trigger's `order by created_at desc limit 1` isn't exploitable via a decoy second instance; no code path anywhere in `packages/services` performs a direct `UPDATE`/`DELETE` on `workflow_instances` outside `record_workflow_decision`, so the INSERT-only narrowing breaks nothing; the procurement trigger fires `BEFORE UPDATE` only (never `INSERT`, so referencing `OLD` cannot error); a `FOR ALL` policy's `WITH CHECK` clause is never evaluated for `DELETE` (Postgres semantics), so the new attendance guard cannot spuriously block a delete (moot regardless, since no delete path exists for `attendance` in this codebase today); all six `revoke`/`grant` statements in 0039 exactly match their functions' live signatures, with no silent no-op from a signature mismatch; and every remaining caller of `event_participants`/`playlists` already only ever reads its own caller's row.

## 5. Seed data changed this phase

None. All six fixes are RLS-policy replacements, new triggers, or grant statements — no new table, column, or seed row.

## 6. Validation performed

- **A full, fresh migration apply** (`scripts/db-migrate.sh` against a clean local Postgres 16 database, mirroring CI's `migration-check` job exactly) plus the reference seed data — clean, no errors, run twice (once after the initial four migrations, once again after 0036's post-review fix).
- **Manual, scenario-by-scenario verification against real Postgres** for every one of the six fixes, both the "should now be blocked" and "legitimate path still works" side of each: the expense/gate-pass/invitation bypass attempts (blocked), the legitimate `record_workflow_decision`-then-sync path for approval, rejection, AND cancellation (all three succeed, including invitations' real `record_workflow_decision('reject', ...)` → `'declined'` sync, which is what the security review's own caught bug would have broken), a direct `workflow_instances` overwrite (0 rows affected), the procurement illegal-jump (blocked) and legal transition (succeeds), the attendance audit trigger firing and a mismatched `recorded_by` being blocked while a matching one succeeds, `playlists.shared_with_roles` granting a listed role visibility while an outsider still can't see it, and `event_participants` hiding another member's row from an unrelated signed-in user while the row's own owner still sees it.
- **`pnpm typecheck`/`pnpm lint`/`pnpm --filter @ngc/services test`** across all 8 workspace packages — clean, 458/458 unit tests passing (unaffected by these DB-only changes, as expected).
- **`pnpm --filter @ngc/web build`** — succeeds.
- **The full Playwright e2e suite (77/77)** — passes unchanged; expected, since the mock server this suite runs against does not enforce RLS at all (see above) and so cannot regress from or validate a pure RLS/trigger change either way — real-Postgres manual verification is the load-bearing check for this sub-phase, not the e2e suite.
- **An independent adversarial security review** — one real, would-have-shipped bug found and fixed (§4); everything else confirmed sound.
