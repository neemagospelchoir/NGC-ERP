# PHASE_12_1.md — Phase 12.1 Deliverable
## Neema Gospel Choir (NGC) ERP — Mobile: Foundation

Phase 12 ("Mobile", per `docs/ARCHITECTURE.md`'s numbered build order) is decomposed into sub-phases — the surface area (a whole new client platform, offline sync, QR codes, and ~13 V1 screens per PRD/ARCHITECTURE §9) is far larger than any single-table module built in Phases 7–11, and the Development Control Rule's "sub-phases continue automatically once the phase is authorized" convention applies exactly as it did for Phases 7–10. This sub-phase is Foundation: the Expo/React Native app itself, its navigation shell, its own Supabase client, a hand-ported theme, and the first two real screens (Dashboard, Profile) proving the whole stack — auth, shared `packages/services` calls, RLS-scoped reads, rendering — works end-to-end on this new client. Member self-service modules (attendance, leave, events, announcements, notifications) are 12.2; QR codes, voting, contributions, and application status are 12.3.

## 1. Scope

In scope:
- **`apps/mobile`** stood up as a real Expo SDK 57 + React Native 0.86 + TypeScript app (previously a placeholder `package.json` only, with all three scripts echoing "no source yet" — see §7 of every prior phase's validation section referencing `@ngc/mobile: no source yet`).

- **Dashboard and Profile screens**, reading `user` from `AuthProvider` and (Dashboard only) calling `attendance.getMemberAttendanceSummary` unchanged from `@ngc/services` — proving a real RLS-scoped read works from this client.
- **A cross-workspace pnpm/TypeScript conflict, found and fixed** — see §2.1. Not part of the mobile app itself, but a real regression this phase's dependencies introduced into `apps/web`'s typecheck, caught before this phase was considered complete.

## 2. Architecture

### 2.1 A cross-workspace pnpm + TypeScript conflict, found and fixed

Adding `apps/mobile` as a real Expo SDK 57 app introduced this workspace's first-ever second major version of React: mobile requires React 19 + `@types/react@19` (Expo SDK 57's own hard requirement), coexisting with `apps/web`'s existing React 18 + `@types/react@18`. This is unavoidable — Next.js 14 (this app's existing, already-built web stack) does not support React 19, and downgrading Expo SDK 57 to React 18 is not an option Expo offers.

Once both existed anywhere in the pnpm store, `apps/web`'s own `tsc --noEmit` broke with a spurious error:
```
app/layout.tsx(14,24): error TS2322: Type 'React.ReactNode' is not assignable to type '...@types+react@18.3.31.../ReactNode'.
  Type 'bigint' is not assignable to type 'ReactNode'.
```
**Root cause, confirmed via `tsc --traceResolution`**: `next`'s own bundled `.d.ts` files (`next/dist/**/*.d.ts`) do a bare `import ... from "react/jsx-runtime"` for their own internal typing needs. `next` does not declare `@types/react` as a real `package.json` dependency (it's DefinitelyTyped — consumed only by `tsc`, never at runtime), so pnpm has no dependency edge to nest a correctly-scoped, per-instance copy of `@types/react` alongside that specific resolved `next` instance. Without one, TypeScript's module resolution for that bare specifier walks up past `next`'s own `node_modules`, straight into pnpm's shared internal compatibility-hoist folder (`node_modules/.pnpm/node_modules`) — which holds only **one** version of `@types/react` for the entire workspace. With two incompatible majors now requested (18.x by web, 19.x by the Expo ecosystem — many more packages, so more likely to "win" the shared slot), it hoisted the 19.x copy. That mismatched copy then collided with the correctly-resolved 18.x copy used elsewhere in the same program (via `@ngc/ui`'s explicit `import ... from "react"`), producing the `ReactNode`/`bigint` mismatch above (React 19's `ReactNode` union includes `bigint`; React 18's does not).

**Ruled out before landing on the real fix**:
- Restricting `apps/web/tsconfig.json`'s `"types"` array — doesn't touch this, since the collision happens via an explicit module-specifier resolution inside `next`'s own `.d.ts` files, not via TypeScript's automatic ambient-type auto-inclusion.
- Adding `tsconfig.json` `"paths"` overrides remapping `"react"`/`"react/jsx-runtime"` to this app's own node_modules — technically intercepts the resolution, but breaks React's own global JSX namespace merging program-wide (tested: turned the single `layout.tsx` error into ~80 cascading `IntrinsicAttributes`/`JSX.IntrinsicElements` errors across the whole app). Reverted in full.
- Adding `react`/`@types/react` as direct devDependencies of the workspace root `package.json`, hoping pnpm would weight root-level requests when resolving the shared hoist slot — installed successfully but had no effect on which version won the hoist. Reverted.
- `pnpm.overrides` — would force one global version for `react`/`@types/react` across the **entire** workspace, including inside Expo/React Native's own dependency tree, which genuinely needs 19.x. Not viable; not attempted.

**Actual fix**: `package.json`'s `"pnpm": { "packageExtensions": {...} }` field (pnpm's own documented mechanism for "this package is missing a dependency edge it actually needs"):
```json
"pnpm": {
  "packageExtensions": {
    "next@14.2.35": {
      "dependencies": {
        "@types/react": "18.3.31",
        "@types/react-dom": "18.3.7"
      }
    }
  }
}
```
This makes pnpm treat `next`'s specific resolved instance as if it *actually* declared `@types/react`/`@types/react-dom` as dependencies, nesting them directly inside that instance's own `node_modules` — where its `.d.ts` files' resolution now finds them locally, before ever reaching the ambiguous shared hoist folder. Confirmed via the same `tsc --traceResolution`/`--listFiles` check: only `@types+react@18.3.31` appears in `apps/web`'s program afterward, zero trace of `19.2.18`. Pinned to the exact versions `apps/web` already uses (not a loose range) so this can't silently drift. `pnpm-lock.yaml` records a `packageExtensionsChecksum` confirming the extension is active and versioned with the lockfile.

This required first attempting the config in `pnpm-workspace.yaml`'s own `packageExtensions:` key, which pnpm 9.0.0 (this workspace's pinned version) silently ignored — no error, no effect, lockfile never gained a checksum. Moving the identical config to `package.json`'s `"pnpm"` field (the longer-supported location) made it take effect immediately. Left as `package.json`, not filed as a pnpm-version upgrade task, since it works correctly as configured.

**Verified end-to-end after the fix**: `apps/web` production build (`next build`) succeeds; all 69/69 Playwright e2e tests pass; all 390/390 `@ngc/services` unit tests pass; workspace-wide `pnpm typecheck`/`pnpm lint` are clean across all 8 packages (`@ngc/mobile` included).

### 2.2 Session storage: SecureStore, not AsyncStorage — a security-review finding fixed before ship

The first working version of `src/lib/supabase.ts` used `@react-native-async-storage/async-storage` for the Supabase auth session (access + refresh JWT) — the standard tutorial-level pattern, and what ships in most Supabase-for-Expo quickstarts. An adversarial security review of this phase (dispatched independently of the implementation, §4) flagged it: AsyncStorage is plain, **unencrypted** on-device storage (SharedPreferences/SQLite on Android, a plist on iOS) — readable via a backup-extraction attack, on a rooted/jailbroken device, or by another app's storage on a compromised device. For an institutional ERP carrying member PII behind that session, that is a real hardening gap, not a theoretical one.

**Fix**: `src/lib/secure-storage.ts` now backs the Supabase client with `expo-secure-store` (iOS Keychain / Android Keystore) instead. SecureStore's own caveat is what required the extra file: Android's underlying storage caps a single value at roughly 2048 bytes, and a serialized Supabase session (access token + refresh token + decoded JWT claims) can exceed that, especially as this app's own custom claims grow. `src/lib/chunked-storage.ts` implements a chunk/reassemble/manifest scheme (1800-byte chunks, comfortably under the cap) so no individual SecureStore write ever risks the limit regardless of session size, with two correctness properties enforced and tested: shrinking a value deletes its now-stale trailing chunks (no orphaned Keychain/Keystore entries), and a partially-evicted chunk set is treated as "no session" rather than silently reassembled with a hole in the middle (so a corrupted read fails safe — "please sign in again" — rather than handing Supabase a mangled token string).

`chunked-storage.ts` is deliberately free of any `expo-secure-store`/`react-native` import (the pure chunking algorithm only, taking a `KeyValueBackend` as a parameter — mirroring `packages/services`' own established "accept a client, don't import a factory" convention) specifically so it can be unit-tested: importing `expo-secure-store` transitively pulls in `react-native`'s own Flow-syntax source, which `tsx --test`'s plain-Node/esbuild transform cannot parse at all (confirmed by trying — `Unexpected "typeof"` inside `react-native/index.js`). `secure-storage.ts` is the thin thirteen-line wiring of that algorithm to the real native module; it is not unit-tested itself, exercised only by the `expo export` bundling step and (eventually) real on-device verification — the same "some things this sandbox genuinely cannot verify, named rather than glossed over" honesty this codebase applies elsewhere (`docs/AUTHENTICATION.md` §4's mock-server rationale; §6 below).

### 2.3 Mobile theme: hand-ported token values, not a shared import

`packages/ui/src/` contains `components/` (React DOM components — not reusable by React Native, which has entirely different primitives), `index.ts`, `tokens.css`, and `utils/` — confirmed via `find packages/ui/src -iname "*token*"` that `tokens.css` is the *only* token artifact; there is no sibling `.ts`/`.js` export of the same values usable outside a CSS pipeline. `src/theme/tokens.ts` hand-replicates the semantic color roles (brand, status, ink/surface, radius, spacing) `tokens.css` defines, as plain TypeScript objects for both light and dark modes. Deliberately **not** ported: the data-viz ramps (`series-1..8`, `sequential-*`) — no V1 mobile screen renders a chart, and copying an unused ramp only risks silent drift from the web source of truth. `src/theme/tokens.test.ts` guards the one real failure mode a hand-copy like this has: `lightColors` and `darkColors` drifting to different key sets (a typo'd or renamed key in one but not the other), which would otherwise silently produce `undefined` wherever a component reads that token in the "wrong" theme. It does not and cannot verify the hex values themselves still match `tokens.css` — that stays a manual re-check, same as any other hand-copied constant in this codebase, and is called out explicitly rather than implied to be automated.

`useTheme()` follows React Native's `useColorScheme()` (the OS setting) directly — see §1's "explicitly deferred" note on why this is a smaller, deliberate scope than web's own persisted-toggle theme system, not an inconsistency overlooked.

### 2.4 Monorepo wiring: Metro, not webpack/SWC

`apps/mobile/metro.config.js` adds the two settings an Expo app inside a pnpm workspace needs to resolve `@ngc/services`/`@ngc/db` (raw TypeScript source one level up in the monorepo, outside this app's own `node_modules`) and pnpm's symlinked package layout: `watchFolders` pointing at the workspace root, and `resolver.unstable_enableSymlinks = true`. Deliberately **not** set: `resolver.disableHierarchicalLookup`, despite that being part of Expo's own documented Yarn/npm-workspace monorepo recipe — tested and confirmed it breaks resolution of a package's *own* nested dependencies under pnpm's strict, per-package `node_modules` layout (`expo-router`'s own dependency on `@expo/metro-runtime` failed to resolve with it on: `Unable to resolve module @expo/metro-runtime`). Turning hierarchical lookup back on lets Metro find both cases: local per-package dependencies (via the normal walk-up, now following symlinks) and the cross-workspace `@ngc/*` packages (via `watchFolders`/`nodeModulesPaths`).

## 3. UI

- `app/index.tsx` — the app's only unconditional entry point; shows a spinner while the initial session check is in flight, then redirects to `(app)/dashboard` or `(auth)/login`. No other screen makes this decision, so there is exactly one place a cold launch's routing logic lives.
- `app/(auth)/login.tsx` — email + password sign-in, reusing `auth.signInWithPassword` unchanged. Its own group layout (`app/(auth)/_layout.tsx`) redirects a signed-in user straight to the dashboard — nobody who's already authenticated has a reason to see this screen.
- `app/(app)/dashboard.tsx` — a greeting, the caller's roles, and (only if a `member` record is linked to the account — an Applicant/Guest-persona user may have none, per ARCHITECTURE's own persona list, and that is a normal state, not an error) their attendance summary via `attendance.getMemberAttendanceSummary`, unchanged from `@ngc/services`.
- `app/(app)/profile.tsx` — the signed-in user's own profile fields (name, email, member number, membership status, roles) and a sign-out button. Its own group layout (`app/(app)/_layout.tsx`) redirects a signed-out user to login.

## 4. Security review

An adversarial review (Agent-dispatched, independent of the implementation) covered the new Supabase client, `AuthProvider`, all route-guard layouts, and the theme files, against the specific threat model a *native* client has that the web app (SSR + httpOnly cookies via `@supabase/ssr`) does not. Findings:

- **Session tokens stored unencrypted via `AsyncStorage` — real hardening gap, fixed before ship.** See §2.2. This was the review's one substantive finding; addressed via `expo-secure-store` + the chunking adapter described there, not merely noted and deferred.
- **No other issues found.** Route guards fail closed correctly (`app/index.tsx` shows only a spinner during `"loading"`, never renders gated content before the session check resolves; `AuthProvider`'s own `loadUser()` failure path treats an error as signed-out, never fail-open). No screen renders member data without the same `user`/`user.member` null-checks the dashboard already demonstrates. The anon key is only ever used as the public, RLS-gated credential `createClient` expects — no service-role key or elevated trust anywhere in mobile code. No hardcoded secret, URL, or credential in any new file — `getSupabaseClient()` throws loudly if its required env vars are missing rather than falling back to a default. The dashboard's attendance read relies entirely on `attendance_select_scoped` RLS (unchanged from Phase 7.3) to scope results to the caller's own data; no bypass attempted.
- **Noted, not a defect**: `(app)/_layout.tsx`'s `<Tabs>` shell renders during the `"loading"` auth state (before the redirect-away-if-signed-out check can fire), rather than showing nothing. No data or capability is exposed during that window — every screen's own null-checks already handle `user` being absent — so this is a minor UX nit (a flash of an empty tab shell), not a security issue.
